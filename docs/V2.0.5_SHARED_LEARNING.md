# Shared interval analysis

User-approved policy (2026-09-25 JST): aggregate new answers across linked devices; preserve historical device-local analysis separately without importing it.

- `learning_answers` stores immutable answer events, indexed uniquely by player and event UUID. Acknowledgement loss and concurrent tabs can resend safely.
- The frontend persists one event per local storage key, scoped to backend, authentication identity, and player. Registered practice, standard, EAR, HD, and assignment answers use the same capture path; guest answers stay local.
- The server's insert and aggregate functions run with caller privileges and ownership RLS. Unlinked users cannot read or submit, wrong-owner submissions are denied, and suspended accounts cannot insert. No public ranking row is created by answering practice questions.
- HISTORY shows only synchronized new answers in shared analysis. Its sample threshold remains three answers per interval. It does not sum old cumulative snapshots. Mean response time is computed from new events for the shared weakness tie-break; the historical EMA remains in the archived local data.
- On first loading the new script in an origin, the existing mastery object is copied once to `intervalCosmos.mastery.legacy.v205`. The existing mastery object continues to support the existing game/adaptive/result experience. The frozen copy is never uploaded and is displayed in a separate HISTORY disclosure.
- Events are retried on reconnection, visible-page activation, a short debounce after answers, every 30 seconds, and opening HISTORY. Storage failure is reported in the analysis note; pending IDs are retained after network or authorization failures.
- Shared analysis deliberately excludes old application versions' answers until those devices upgrade. Unsubmitted local events are not merged into the shared total, avoiding ambiguity after a lost server acknowledgement.

## Deployment

Apply `supabase/migrations/20260924145138_shared_learning_answers.sql` as an incremental migration before serving the new frontend. Applied only to the dedicated Fresh Build Test project during development; production migration is not authorized by this work.

The complete bundle builder and psql runner include this migration. Never run a full fresh-build bundle on an existing database.

## Security validation

`tests/learning-sync-v205.sql` uses a synthetic linked account specified through `app.qa_player_id`. It rolls back all test writes and temporary suspension. Covers duplicate delivery, aggregate availability, direct cross-player insert rejection, RPC ownership, invalid interval rejection, suspended sender, unlinked read/write denial, and anon RPC denial.

Supabase advisor warns about anonymous-auth roles, as it does for existing ownership policies. This app intentionally uses anonymous Supabase Auth identities linked to registered players. Ownership requires `current_player_id()`; unlinked anonymous sessions cannot read these rows. See [anonymous-access advisor](https://supabase.com/docs/guides/database/database-advisors?queryGroups=lint&lint=0012_auth_allow_anonymous_sign_ins). No new security-definer functions were introduced.

## Stalled transport follow-up

New-answer upload and shared-analysis reads now have a 15-second wait limit. A timed-out request can still reach the server later; the original event IDs remain queued, so later retries are deduplicated. Periodic retry remains 30 seconds. This limit applies to the new analysis path, not every existing cloud call.

`tests/learning-stall-browser.html` exercised an indefinitely pending mock upload: after 15 seconds the UI regained control with one pending answer and zero received events. A recovery attempt coinciding with an already-running periodic retry waited for that retry to time out; the next retry cleared the queue with exactly one received event. Node tests also cover a late acknowledgement after timeout and rejecting an analysis response after the active account changes. All 29 Node suites and the fresh-server isolation test passed.
