# INTERVAL COSMOS v2.0.5 — Phase 1 Architecture

## Purpose

v2.0.5 separates a **player account** from the Supabase anonymous Auth user attached to a browser/device.
This is required for secure multi-device linking while preserving anonymous sign-in and RLS.

## Core identity model

### `players`
One row per real INTERVAL COSMOS account.

Planned fields:
- `id uuid` — INTERVAL COSMOS player ID
- `account_type` — `student` / `staff`
- `student_number` — student only; normalized digit string; never public
- `player_name`
- `course_code` — student course; null for staff
- `avatar_id` — custom avatar identifier; staff uses dedicated teacher avatar
- `ranking_visibility` — `ask` / `always_public` / `always_private`
- `main_title_id`
- `equipped_frame_id`
- `achievement_points`
- `is_suspended`
- timestamps

Guest mode remains local-only and does not create a `players` row until the guest converts to a formal account.

### `player_devices`
Maps one or more Supabase Auth users/devices to one INTERVAL COSMOS player.

- `auth_user_id uuid` → `auth.users(id)`
- `player_id uuid` → `players(id)`
- timestamps

A new browser/device can have its own anonymous Supabase Auth user while still controlling the same `player_id` after PIN linking.

### Why this is necessary

v2.0.4 uses `profiles.id = auth.users.id`. That makes one browser identity equal one player identity, which prevents clean multi-device use.
v2.0.5 changes the relationship to:

`auth.users (device session)` → `player_devices` → `players (real account)`

This lets both old and new devices remain logged in simultaneously.

## Student number normalization

Student numbers are strings, never numbers.
Before uniqueness checks:
- convert full-width digits to ASCII digits
- strip commas
- strip spaces and other non-digits
- preserve leading zeroes

Uniqueness applies to the normalized student-number value for student accounts only.

## Public/private separation

Student numbers and private learning data must not be queryable by other players.

Planned public data is separated from private account data so ranking/profile-card reads never expose private fields.
Public profile information may include:
- player name
- course badge
- avatar
- main title
- equipped frame
- public achievement highlights
- public aggregate records

Never public:
- student number
- device/auth IDs
- detailed play timestamps
- detailed weakness history
- private assignment/learning records

## Rankings

Best records remain monthly + all-time.
Each ranking record gains a public/private state.

The server must be able to return a **rank equivalent** even when the player's record is private.
Only public records appear in the public ranking list.

Ranking visibility preference:
- `ask` (default)
- `always_public`
- `always_private`

A rank-in animation is shown only when the current result actually improves the relevant stored best/rank record.

## Play history / learning analytics

Every completed run receives a client-generated unique event ID.
This enables offline queueing and prevents duplicate uploads after reconnect.

Planned session record includes:
- `client_event_id`
- player ID
- mode
- score
- correct / total
- max combo
- average response
- interval-level statistics (JSONB)
- played timestamp
- optional assignment ID

If two devices update a best record, server-side conflict handling keeps the higher score.

## PIN device linking

Planned flow:
1. Existing linked device requests a six-digit PIN.
2. PIN expires after approximately five minutes.
3. New device enters PIN.
4. Existing device confirms the new-device request.
5. New device's anonymous Auth user is added to `player_devices` for the same player.
6. PIN becomes unusable.
7. Both devices remain valid.

PIN values should not be stored as plain text; store a server-side hash plus expiry/usage state.

## Staff / administration

`account_type = staff` uses a dedicated teacher avatar and no staff/student number.
Administrative capability is separate from being staff (planned `is_admin` or equivalent server-authorized role), so not every staff account automatically receives destructive powers.

Admin operations include:
- edit profile
- change course
- hide ranking
- delete ranking
- suspend account
- fully delete account after confirmation
- view learning history
- create/manage common assignments

Service-role/secret credentials must never be shipped to the browser.
Destructive Auth operations will be handled by server-side Supabase functionality (e.g. Edge Functions).

## Achievement / profile growth model

Planned persistent concepts:
- achievement catalog
- unlocked achievements
- achievement points
- title catalog / owned titles
- frame catalog / owned frames
- main title selection
- equipped frame selection

Normal frame progression is point-based (Bronze → Silver → Gold → Platinum → Cosmic → higher dynamic tiers).
Special frames can require combinations of specific achievements.
High-end hidden achievements display as `???` until unlocked.

## Assignments

Assignments are common to all students rather than join-code based.

Fields include:
- title / description
- target mode
- interval set
- question/time condition
- start time
- deadline
- target score / accuracy

Students may retry any number of times before the deadline; the best submission is retained.

## Offline synchronization

Offline runs are queued locally with unique event IDs.
On reconnect:
- upload automatically
- ignore duplicate event IDs
- recompute best records server-side
- keep the higher best if multiple devices raced

## Migration principle

The production v2.0.4 database must not be dropped.
Migration will be additive/non-destructive:
1. create new account/device structure
2. migrate existing v2.0.4 profile rows into players
3. map existing Auth IDs as each player's first device
4. migrate existing ranking ownership to player IDs
5. enable new RLS/functions
6. retain a rollback path until verification completes

Do not run the Phase 1 migration against production until the migration SQL has been reviewed and the v2.0.4 stable branch is confirmed.
