# INTERVAL COSMOS v2.0.5 — Phase 1 Architecture

## Purpose

v2.0.5 separates a **player account** from the Supabase anonymous Auth user attached to a browser/device.
This is required for secure multi-device linking while preserving anonymous sign-in and RLS.

## Core identity model

### `players`
One row per real INTERVAL COSMOS account.

Planned fields:
- `id uuid` — INTERVAL COSMOS player ID
- `account_type` — `student` / `staff`
- `student_number` — student only; normalized digit string; never public
- `player_name`
- `course_code` — student course; null for staff
- `avatar_id` — custom avatar identifier; staff uses dedicated teacher avatar
- `ranking_visibility` — `ask` / `always_public` / `always_private`
- `main_title_id`
- `equipped_frame_id`
- `achievement_points`
- `is_suspended`
- `is_admin`
- timestamps

Guest mode remains local-only and does not create a `players` row until the guest converts to a formal account.

### `player_devices`
Maps one or more Supabase Auth users/devices to one INTERVAL COSMOS player.

- `auth_user_id uuid` → `auth.users(id)`
- `player_id uuid` → `players(id)`
- timestamps

A new browser/device can have its own anonymous Supabase Auth user while still controlling the same `player_id` after PIN linking.

### Why this is necessary

v2.0.4 uses `profiles.id = auth.users.id`. That makes one browser identity equal one player identity, which prevents clean multi-device use.

v2.0.5 changes the relationship to:

`auth.users (device session)` → `player_devices` → `players (real account)`

This lets both old and new devices remain logged in simultaneously.

## Student number normalization

Student numbers are strings, never numbers.

Before uniqueness checks:
- convert full-width digits to ASCII digits
- strip commas
- strip spaces and other non-digits
- preserve leading zeroes

Uniqueness applies to the normalized student-number value for student accounts only.

## Public/private separation

Student numbers and private learning data must not be queryable by other players.

Public data is mirrored separately so ranking/profile-card reads never expose private fields.

Public profile information may include:
- player name
- course badge
- avatar
- main title
- equipped frame
- achievement points
- selected public achievement highlights
- public aggregate ranking records

Never public:
- student number
- device/auth IDs
- admin flags
- detailed play timestamps
- detailed weakness history
- private assignment/learning records

## Rankings

Best records remain monthly + all-time.

v2.0.5 separates:
- **actual best** — the player's real best, public or private
- **public best** — the best session the player has explicitly allowed on the leaderboard

This allows a player to set a new private personal best without erasing an older public leaderboard record.

The server can return a **rank equivalent** for the private best by comparing it with public leaderboard records.
Only public records appear in the public ranking list.

Ranking visibility preference:
- `ask` (default)
- `always_public`
- `always_private`

For `ask`, an improved record is stored privately first, and the client can call a publication RPC after the player chooses “公開する”.

A rank-in animation is shown only when the current result actually improves the relevant stored best record.

## Play history / learning analytics

Every completed run receives a client-generated unique event ID.
This enables offline queueing and prevents duplicate uploads after reconnect.

Session records include:
- `client_event_id`
- player ID
- source (`ranked` / `practice` / `assignment`)
- mode
- score
- correct / total
- max combo
- average response
- interval-level statistics (JSONB)
- played timestamp
- optional assignment ID
- publication state

If two devices update a best record, server-side conflict handling keeps the higher score.

## PIN device linking

Planned flow:
1. Existing linked device requests a six-digit PIN.
2. PIN expires after approximately five minutes.
3. New device enters PIN.
4. Existing device confirms the new-device request.
5. New device's anonymous Auth user is added to `player_devices` for the same player.
6. PIN becomes unusable.
7. Both devices remain valid.

PIN values are not stored as plain text; the database stores a hash plus expiry/usage state.

The public browser must not receive any Supabase secret/service-role credential.
PIN verification/confirmation will be implemented with reviewed server-side logic in Phase 2.

## Staff / administration

`account_type = staff` uses a dedicated teacher avatar and no staff/student number.

Administrative capability is separate from being staff:
- a staff account does **not** automatically become an administrator
- `is_admin` or equivalent server authorization controls destructive actions

Public self-registration as `staff` is disabled in the Phase 1 database.
Staff accounts will be created/approved by administrator-controlled server-side flow so students cannot impersonate staff.

Admin operations include:
- edit profile
- change course
- hide ranking
- delete ranking
- suspend account
- fully delete account after confirmation
- view learning history
- create/manage common assignments

Secret/service-role credentials must never be shipped to the browser.
Destructive Auth operations will be handled by server-side Supabase functionality such as Edge Functions.

## Achievement / profile growth model

Persistent concepts:
- achievement catalog
- unlocked achievements
- achievement points
- title catalog / owned titles
- frame catalog / owned frames
- main title selection
- equipped frame selection

Normal frame progression is point-based:
`NORMAL → BRONZE → SILVER → GOLD → PLATINUM → COSMIC → higher dynamic tiers`

Special frames can require combinations of specific achievements.
High-end hidden achievements display as `???` until unlocked.

The initial Phase 1 schema seeds only the base frame tiers.
The detailed achievement/title/frame catalog will be populated in the later achievement phase.

## Assignments

Assignments are common to all students rather than join-code based.

Fields include:
- title / description
- target mode
- interval set
- question/time conditions
- start time
- deadline
- target score / accuracy

Students may retry any number of times before the deadline.
The best submission is retained and attempt count is recorded.

Assignment attempts do not automatically participate in the normal public ranking because assignment conditions may differ from standard ranked play.

## Offline synchronization

Offline runs are queued locally with unique event IDs.

On reconnect:
- upload automatically
- ignore duplicate event IDs
- recompute best records server-side
- keep the higher best if multiple devices raced

## Fresh-build principle for v2.0.5

As of 2026-08-17, INTERVAL COSMOS has **not yet been distributed to students**.
Only the developer/teacher has created test accounts.

Therefore v2.0.5 does not need to preserve v2.0.4 test player/ranking data.

The Phase 1 database setup is intentionally a fresh build:
1. keep Git branch `v2.0.4-stable` as the rollback reference
2. drop the v2.0.4 application tables (`profiles`, `rankings`)
3. create the v2.0.5 catalogs/account/device/history/ranking/assignment/growth tables
4. enable RLS
5. expose only reviewed RPCs to authenticated clients
6. leave `auth.users` untouched by the setup SQL; test Auth-user cleanup is handled separately

This greatly simplifies the new account model and avoids carrying temporary v2.0.4 constraints into the release design.

Do not merge `v2.0.5-dev` into `main` until database verification, account tests, ranking privacy tests, multi-device tests, and rollback checks have passed.
