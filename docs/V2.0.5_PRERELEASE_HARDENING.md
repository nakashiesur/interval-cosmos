# v2.0.5 Pre-release hardening

## 1. Supabase client unification — IMPLEMENTED / FINAL BROWSER CHECK REQUIRED

実ブラウザのDevToolsで以前、以下の警告を確認。

`Multiple GoTrueClient instances detected in the same browser context.`

### 原因

認証を所有する `cloud.js` とは別に、recovery / progression等が追加のSupabase clientを生成していた。

### 対応済み

`supabase-singleton-v205.js` を `cloud.js` より前に読み込み、同一Project URL / keyに対する `createClient()` をブラウザコンテキスト内で1インスタンスへ統一。

- `cloud.js` が最初に生成したclientを共有
- 後段モジュールが `createClient()` を呼んでも同一clientを返す
- Assignments / Admin Dashboardは共有singletonを明示利用
- 認証storage ownerを複数生成しない

### リリース前の実ブラウザ確認

1. 既存学生アカウントの自動ログイン
2. 6桁PINによる別端末追加
3. 学籍番号＋復旧コードによる自己復旧
4. ランキング取得・公開
5. 学習履歴取得
6. MY COSMOS取得
7. 実績・デイリー進行
8. 代表実績の保存
9. Assignments / Admin Dashboard
10. DevTools Consoleに `Multiple GoTrueClient` 警告が出ないこと

専用テスト環境のブラウザで一部を確認済み。端末幅のiframe検証は実機検証とは区別する。未完のアカウント経路と実機マトリクスを検証し、最終リリース候補でConsole警告も再確認する。

## 3. Offline queue — IMPLEMENTED / targeted integration PASS

2026-09-15: ランキング／課題の結果を送信前に端末へ保存し、接続復帰後に同じ `client_event_id` で再送する仕組みを実装。送信済み／送信待ち／確認が必要な記録は「保存・同期」から確認できる。保存先DB・認証ID・プレイヤーIDを区別し、異なるアカウントへ再送しない。

新しい `submit_saved_play` RPC は本人と公開設定をトランザクション内で検査。公開設定が変わった記録は停止し、現在の設定を本人が確認するまで送らない。課題は終了時刻を保持し、既存の期限判定へ渡す。拒否された記録も端末に残す。保存領域不足を「保存済み」と扱わない。

既存DBには `supabase/migrations/20260915032833_offline_submission_guard.sql` の追加適用が必要。専用Fresh Build Testプロジェクトへ適用・DB回帰PASS。本番／通常開発DBへの適用は未実施。端末再起動、物理的な機内モード、ブラウザ保存容量の実機差を含むPhase 12は継続する。

2026-09-17: 実ゲームの通信をテスト用workerで遮断し、オフライン起動→TEXT終了→端末保存→切断中リロード→再接続→同期を確認。80点の記録は元の終了時刻を保持し、テストDBに非公開で1件だけ保存された。実ネットワーク障害の再現であり、OSの機内モード試験ではない。SDKの読み込み失敗からの再試行、および再接続中に終了したゲームの保存も回帰テストで保護する。
