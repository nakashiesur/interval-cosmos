# HTTPS physical-device staging

Build with `python3 scripts/build-device-test-site.py <new-directory>`.
This exports the same 150 allowlisted app assets as the LAN preview, replacing
cloud-config.js with the dedicated Fresh Build Test public client configuration.
No production configuration, SQL, repository metadata, tests, or work notes are
included. Existing output directories are refused. Nothing is deployed by this
command; it performs no database operations.

Host the directory at the root of a separate HTTPS site. `_headers` includes
revalidation rules for hosts supporting that format. Do not deploy this over the
production site or merge main. A hosting destination and authorization to expose
the test frontend must be established before publishing. Public hosting exposes
the test frontend and its public client key, not administrator credentials.

After deployment, verify the effective backend configuration and successful
service-worker install/cache population before requesting physical tests.

Batch for both physical devices, using synthetic accounts only:
1. Online first load and normal audio/play/history.
2. Offline cached reload and completed guest play, history retained after reload.
3. Reconnect and verify UI recovery.
4. For an approved linked synthetic account: offline play, reload while offline,
   reconnect, exactly one saved session in the backend and second device.
5. Repeat reconnect to ensure no duplicate score.
6. Home-screen installation, closed/reopened installed app and audio after lock.
7. Return after long idle without reload, REPLAY and another mode.

Current LAN HTTP origin cannot substitute for these secure-context tests.
Physical guest UI checks already passed; do not repeat all of them unnecessarily.
